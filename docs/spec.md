# Спецификация мини-CRM «Объекты и задачи»

Статус: реализована локальная версия; покрытие и ограничения проверки — в `verification.md`. Дата: 2026-11-13.
Подход: Specification-Driven Development (SDD): спецификация → контракты → проверки → реализация → доказательства выполнения.
Этот файл определяет поведение; `implementation-plan.md` — порядок реализации.
Изменения поведения сначала отражаются здесь, затем в проверках и коде.

Исходники разделены на `frontend/` (React/FSD) и `backend/` (Supabase/PostgreSQL,
миграции, серверные правила и backend-тесты). Общие команды запуска находятся в корне.

## 1. Границы продукта

Одна строительная компания, несколько постановщиков и исполнителей.
Обязательны вход, объекты, задачи, разрешённые переходы, история и разграничение доступа в базе.
Вне MVP: организации/тенанты, регистрация, управление пользователями в интерфейсе,
вложения, уведомления, сроки задач, поиск, realtime, отдельный HTTP-сервер.

## 3. Статусы

| Из            | В                         | Кто                     | Дополнительное условие          |
| ------------- | ------------------------- | ----------------------- | ------------------------------- |
| —             | `new` — Новая             | Постановщик             | Только создание задачи          |
| `new`         | `in_progress` — В работе  | Назначенный исполнитель | —                               |
| `in_progress` | `in_review` — На проверке | Назначенный исполнитель | —                               |
| `in_review`   | `accepted` — Принята      | Постановщик             | —                               |
| `in_review`   | `rework` — На доработке   | Постановщик             | Непустой комментарий после trim |
| `rework`      | `in_progress` — В работе  | Назначенный исполнитель | —                               |

Повторная установка того же статуса не считается переходом и отклоняется.
Из `accepted` переходов нет. Постановщик не выполняет переходы исполнителя.
Обновление обычных полей не меняет статус и не добавляет событие статуса.

## 4. Данные и ограничения

Нормализация: пользователь, объект, задача и событие — отдельные отношения;
названия объектов и имена пользователей не копируются в задачи.
Текущий статус хранится в задаче как состояние агрегата, история — отдельные неизменяемые события;
их согласованность обеспечивается одной транзакцией.

| Таблица              | Поля                                                                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `auth.users`         | Пользователи Supabase Auth; пароли и аутентификация не дублируются                                                                                           |
| `profiles`           | `id` PK/FK → auth.users, `display_name`, `role` enum (`manager`, `executor`)                                                                                 |
| `construction_sites` | UUID PK, `name`, `address`, `created_by` FK, `created_at`, `updated_at`, `version`, `deleted_at` nullable                                                    |
| `tasks`              | UUID PK, `site_id` FK, `title`, `description`, `assignee_id` FK, `status` enum, `author_id` FK, `created_at`, `updated_at`, `version`, `deleted_at` nullable |
| `task_status_events` | UUID PK, `task_id` FK, `actor_id` FK, `from_status` nullable, `to_status`, `comment` nullable, `created_at`, `task_version`                                  |

- Все даты — `timestamptz`, храним в UTC, отображаем в локальном часовом поясе.
- Обязательные поля: название объекта, адрес, название задачи, объект и исполнитель.
- Описание необязательно: пустая строка по умолчанию. Комментарий необязателен кроме возврата.
- Пределы: названия 1–200 символов после trim, адрес 1–500, описание до 10 000, комментарий до 2 000.
- FK защищают связи; назначить можно только существующего исполнителя.
- Автор, время, начальный статус и номер версии задаются базой, не входными данными клиента.
- Уникальность `(task_id, task_version)` защищает от повторного события одной версии.
- Индексы: `tasks(assignee_id, site_id)` для живых задач, `tasks(site_id, created_at, id)` для списков,
  `task_status_events(task_id, created_at, id)` для истории; дополнительные — только под реальные запросы.
- Физическое удаление пользователей с историей запрещено FK; удаление учёток вне MVP.

## 5. Доступ и инварианты безопасности

1. `anon` не читает и не меняет бизнес-данные. RLS включён на всех продуктовых таблицах.
2. `authenticated` получает минимальные явные grants: SELECT с RLS и EXECUTE нужных RPC.
   Прямые INSERT/UPDATE/DELETE бизнес-таблиц запрещены, включая изменение роли и истории.
3. Постановщик читает все неудалённые объекты и задачи. Исполнитель — только назначенные ему задачи,
   связанные с ними объекты и историю этих задач. В карточке общего объекта он не видит задачи коллег.
4. Список исполнителей доступен постановщику. Исполнитель видит свой профиль и минимальные данные
   участников доступных ему задач: ID, отображаемое имя и роль автора/участников истории.
   Auth-таблицы и email других пользователей не экспонируются.
5. Роль читается из защищённого `profiles`, никогда из изменяемого `user_metadata`.
   Проверка роли в RLS использует закрытый helper без рекурсивного чтения policy профилей.
6. Все команды проверяют `auth.uid()`, роль, доступ к записи, допустимые поля, удаление и версию.
   `actor_id`, `author_id`, время и старый статус не принимаются от клиента.
7. `SECURITY DEFINER` применяется только для необходимых команд и закрытых helpers:
   пустой `search_path`, квалифицированные имена, без динамического SQL, минимальные права владельца.
   По умолчанию EXECUTE отозван у PUBLIC/anon; authenticated получает только необходимые вызовы.
   Definer может обходить RLS: каждая такая команда обязана самостоятельно проверить доступ.
8. Смена статуса блокирует задачу `FOR UPDATE`, сверяет `expected_version`, проверяет переход
   и обновляет строку. Триггеры БД проверяют инварианты и создают событие из OLD/NEW и `auth.uid()`.
   Комментарий передаётся триггеру только внутри команды в контексте текущей транзакции;
   helper для его установки не является публичным API. Ошибка откатывает статус и событие вместе.
9. Правила изменения статуса и создания события не зависят только от кода RPC:
   будущий привилегированный путь записи также должен проходить проверку триггером.
10. Смена назначения проверяется по версии; новая задача не может ссылаться на удалённый объект.
    Операции с объектом и его задачами используют согласованный порядок блокировок: объект → задача.
11. Текст показывается как текст, без HTML-интерпретации. Ошибки API не раскрывают чужие записи.
12. Администратор БД остаётся доверенным субъектом: запрет подделки истории относится к продуктовому API,
    а не к владельцу БД, который технически способен изменять схему и данные.

## 6. Принятые допущения

- Ровно одна роль на пользователя. Все постановщики равноправны и видят всю компанию.
- Задача всегда имеет одного исполнителя. Постановщик не назначается исполнителем.
- Переназначение и изменение объекта разрешены постановщику в любом статусе, статус сохраняется.
  Старый исполнитель сразу теряет доступ, новый получает всю историю. Отдельный аудит редактирования вне MVP.
- Создание даёт начальное событие `NULL → new`.
- «Удалить» означает soft delete. Удаление объекта атомарно скрывает объект и его задачи;
  история остаётся в базе, через обычный API недоступна. Восстановление вне MVP.
- Последовательность истории определяется временем БД и версией, а не сортировкой UUID.
- Списки ограничены размером страницы, начальный размер — 20; все выдачи имеют стабильную сортировку.
- На MVP нет событий реального времени: после своих изменений выполняется обновление запросов;
  устаревшая команда получает конфликт, интерфейс предлагает обновить данные.
- Доступы для демонстрации передаются в сообщении при сдаче; пароли не фиксируются в Git.

## 7. Что требуется для сдачи

Рабочий URL; минимум 1 постановщик и 2 исполнителя; 2–3 объекта и задачи в разных статусах.
GitHub-репозиторий с миграциями и README. Полстраницы объяснения руководителю.
Список допущений и честный перечень того, что осталось вне реализации.
Фактическое время начала и ожидаемое время сдачи сообщаются в hh.ru перед началом реализации.
Публикация и отправка сообщения не входят в создание этого плана.

## 8. Доработка после архитектурного аудита

| ID        | Требование                                 | Критерий приёмки                                                                                                                                                                                                                                     |
| --------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CONC-02   | Черновик связан с исходной версией         | Фоновое обновление и конфликт не повышают версию открытой формы; повторное сохранение не затирает чужие поля. Загрузка актуальной записи выполняется явно с предупреждением о замене черновика.                                                      |
| PAGE-01   | Список восстанавливается после сокращения  | Недоступная страница автоматически заменяется последней существующей; смена объекта/фильтра начинает список сначала.                                                                                                                                 |
| PEOPLE-01 | Каталог не обрезается лимитом API          | Выбор исполнителя имеет серверный поиск и страницы по 20 с сортировкой имя + ID; имена участников загружаются по ID отображаемых записей с RLS.                                                                                                      |
| CONC-03   | Независимые задачи не блокируют друг друга | Команды задач берут совместимую SHARE-блокировку объектов, удаление объекта — UPDATE; гонки переноса/удаления не оставляют живых задач у удалённого объекта.                                                                                         |
| RETRY-01  | Повтор создания безопасен                  | UUID запроса создания связан с пользователем, командой и входными данными; повтор после потери ответа возвращает ту же сущность без повторного аудита. Изменённые входные данные с тем же UUID отклоняются. Удалённые сущности повтор не раскрывает. |
| CACHE-02  | Обновляются затронутые данные              | Команда задачи инвалидирует списки задач, её карточку/историю и видимость объектов; профиль сессии и несвязанные карточки не перезапрашиваются.                                                                                                      |
| ARCH-02   | UI не содержит сетевых команд              | API, модель формы/мутации и UI разделены внутри feature; AST-проверка охватывает статические и динамические импорты и публичные API.                                                                                                                 |
| A11Y-01   | Ошибки связаны с полями                    | Невалидное поле имеет aria-invalid и aria-describedby на текст ошибки; диалоги не закрываются во время записи.                                                                                                                                       |
| OBS-01    | Ошибки диагностируются без содержимого CRM | Неожиданные сбои передаются в закрытое серверное хранилище как ID, источник, безопасный код, шаблон маршрута и версия приложения; тексты полей, пароли, токены и исходные сообщения ошибок не передаются. Сбор ограничен по частоте.                 |

Создание получает необязательный `p_request_id uuid`; существующие вызовы без ключа сохраняют поведение.
Диагностический RPC доступен только authenticated, чтение диагностик через продуктовый API запрещено.
Мониторинг ошибок не заменяет внешние алерты, резервное копирование и нагрузочное тестирование.
PERF-01: планы чтения проверяются воспроизводимым EXPLAIN ANALYZE под обеими ролями
на 100 объектах и 10000 задачах с откатом временных данных. Локальные замеры не являются SLA.

PEOPLE-02: назначение выполняется одним полем «Исполнитель» с поиском в раскрывающемся
списке. Поиск не является отдельным полем задачи. После выбора показывается имя;
произвольный текст не назначает человека. Закрытие списка сохраняет прежний выбор.
Поддерживаются клавиатура (стрелки, Enter, Escape, Tab), серверные страницы,
состояния загрузки/ошибки/пустого поиска. Escape сначала закрывает список, затем диалог.
