# Решения и допущения

Исходники разделены на `frontend/` и `backend/`. Служебная структура CLI создаётся
в исключённом из Git `.local/supabase/`; источником миграций и серверной логики является `backend/`.
Общий package.json сохраняет команды из корня, сквозные тесты находятся в `tests/`.

Нормативное поведение: [spec.md](./spec.md).

1. Одна компания и одна роль на пользователя. Все постановщики равноправны.
2. Задача всегда назначена одному исполнителю; постановщик не выполняет переходы исполнителя.
3. Переназначение и перенос между объектами не меняют статус. Прежний исполнитель теряет доступ,
   новый получает всю историю. Отдельный аудит редактирования полей не реализован.
4. Удаление — soft delete. Удаление объекта скрывает его задачи в одной транзакции,
   события сохраняются. Восстановления через интерфейс нет.
5. При создании задачи автоматически создаётся событие `NULL → new`.
6. Принятая задача не открывается заново. Редактировать обычные поля постановщик может и после принятия.
7. Версии защищают все изменения объектов/задач. Конфликт не повторяется автоматически:
   UI обновляет серверные данные, но сохраняет исходную версию черновика до явной загрузки актуальной записи.
8. RLS отвечает за чтение, grants запрещают клиентскую запись в таблицы; команды с definer-правами
   явно проверяют доступ. Триггер отдельно проверяет переход и формирует историю.
9. Для безопасных definer-команд используется отдельная роль `crm_backend`, не владелец всей базы.
   Во время миграции ей временно выдаётся CREATE на схемы для передачи владения функциями, затем отзывается.
10. Интерфейс использует собственные базовые компоненты на Radix/Tailwind вместо полного набора shadcn:
    это сокращает объём UI-кода; Dialog сохраняет focus trap, Escape и доступные заголовки.
11. Списки имеют страницы по 20 записей и восстанавливаются после сокращения выдачи. Исполнители выбираются через серверный поиск с пагинацией; имена участников запрашиваются пакетами по ID.
12. Нет realtime: после своих команд выполняется инвалидация, при возврате на вкладку запросы обновляются.
    Изменения других пользователей во время работы на открытой вкладке обнаруживаются при следующем запросе.
13. Docker Desktop запущен для локального Supabase. Проверены и PostgreSQL/PGlite (в том числе
    применение миграций без SUPERUSER), и настоящий Supabase: pgTAP, Auth/PostgREST и браузерный цикл.
14. Playwright тестирует UI с тестовым HTTP/Auth-адаптером поверх той же миграции и RLS.
    В production этот адаптер не входит; реальная проверка конкуренции выполняется через `test:api`.
    Дополнительно выполнен `test:ui:local` без подмен HTTP/Auth.
15. Нет вложений, уведомлений, срока задачи, открытой регистрации и управления пользователями в UI.
16. Публикация, создание облачного Supabase и GitHub-репозитория зависят от доступов к аккаунтам.
    Работающий публичный адрес нельзя считать готовым до фактического развёртывания и проверки.
17. По выбору пользователя подготовлен локальный запуск. Публикация в облако не выполнялась.
18. Вход по email включён настройкой `auth.email.enable_signup=true`; регистрация закрыта общей
    `auth.enable_signup=false`. На установленной версии CLI отключение email-провайдера запрещает и вход.
    Это поведение проверено настоящими запросами: вход разрешён, signup запрещён.
19. Схема `auth` принадлежит Supabase, и миграционная роль не может произвольно раздавать доступ к ней.
    Поэтому `private.actor_id()` — единственный узкий definer-helper владельца миграций: возвращает
    только `auth.uid()`. Команды и чтение бизнес-таблиц выполняются отдельной ролью `crm_backend`.
20. Серверный скрипт создания профилей получает доступ только к чистой функции нормализации,
    которая используется в CHECK-ограничении. Права на запись задач и аудита service_role явно отозваны.

Лимит тестового 2–3 часа — целевой бюджет. Время разработки, настройки окружения и проверки фиксируется честно;
система не заявляется полностью промышленной по наличию архитектурных слоёв и тестов.

21. Черновик и исходная версия записи хранятся вместе в модели feature. Фоновое обновление не меняет базу редактирования; конфликт блокирует сохранение до явной загрузки актуальных данных.
22. Команды задач блокируют объекты в UUID-порядке через FOR SHARE, затем задачу через FOR UPDATE. Удаление/редактирование объекта использует FOR UPDATE. Изменение родителя между чтением и блокировкой вызывает конфликт.
23. Создание принимает p_request_id. Закрытый журнал связывает ключ с пользователем, командой и входом; форма повторно использует ключ при сетевой ошибке. Закрытие формы начинает новую операцию. Ключи автоматически не удаляются, чтобы не нарушать дедупликацию.
24. API-команды, модели и UI разделены внутри features. Инвалидация адресная; профиль сессии не обновляется после каждой команды.
25. RLS вычисляет набор доступных объектов через закрытый helper, возвращающий только разрешённые текущему пользователю ID.
26. Диагностика не содержит исходных сообщений, содержимого форм и полного URL. Сбор ограничен клиентом и сервером; диагностические таблицы закрыты от продуктового API. Обслуживание описано в operations.md.
27. Vitest обновлён до исправленной ветки 4.1.12. Для typescript-estree используется scoped override minimatch 11.0.8: текущая upstream-зависимость от 10.x уязвима. Совместимость проверена lint/typecheck и тестами; override следует пересмотреть после исправления upstream.
