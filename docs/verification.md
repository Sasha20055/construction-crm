# Проверка реализации

## GitHub Pages (DEPLOY-01)

Подготовлены `.github/workflows/pages.yml`, сборка `build:pages` с base `/construction-crm/`
и HashRouter. Локальная production-сборка проверена в Chrome на статическом сервере без SPA fallback:
префикс assets/lazy chunks, прямая ссылка, обновление карточки, сессия, смена пользователя,
изоляция чужой задачи и изменение статуса. Ошибок загрузки файлов и необработанных JS-ошибок нет.

Проверки после изменения: `check`, `format:check`, `npm test` (128 Vitest + 3 проверки FSD),
`build`, `test:pages` (1 сценарий), `test:e2e` (6 сценариев), `test:ui:local` (1 сценарий).
Валидатор конфигурации принимает publishable/anon и отклоняет пустой ключ, secret и service_role.
Настройки из локального `.env.cloud.local` проверены без вывода значений.

Изменения подготовлены локально, коммит и push не выполнялись. GitHub deploy ещё не запускался:
нужны Pages Source = GitHub Actions и две Repository Variables. Инструкция — `github-pages.md`.
Облачные миграции и seed выполнены пользователем по его выводу CLI; приведённые автоматические
проверки Supabase выполнялись локально.

Дата: 2026-11-13. Окружение: macOS/Chrome, Node 25; целевой Node 22+.
Локальный Supabase: PostgreSQL 17, CLI 2.122.1. Ниже приведены локальные проверки; текущий статус подготовки публикации указан выше.

Актуальные результаты после архитектурного аудита приведены в последнем разделе.
Таблица ниже сохраняет результаты исходной реализации до доработки.

После разделения исходников на `frontend/` и `backend/` повторно проверены сборка,
111 unit/integration-тестов, 15 pgTAP, 4 HTTP-теста, два тестовых браузерных сценария
и сквозной сценарий с настоящим Supabase. Проверены повторный setup и генерация типов.
Данные локальной базы при переносе не сбрасывались. Рабочий каталог CLI — генерируемый `.local/`.

## Артефакты и ограничения

Исходники, миграции, CI, README и объяснение руководителю подготовлены.
Локально созданы 1 постановщик, 2 исполнителя, 3 объекта и 6 задач во всех пяти статусах.
Тестовые объекты автоматически скрываются после реальных API/UI-сценариев, их аудит сохраняется.
Пароль находится только в исключённом из Git `demo-credentials.json`; service key туда не записывается.

Скриншоты Playwright находятся в `test-results/` и исключены из Git. Для live-теста:
`live-desktop.png`, `live-task.png`. При повторном запуске Playwright может очищать эту папку.

GitHub Actions подготовлен. Репозиторий: https://github.com/Sasha20055/construction-crm. Удалённый CI для изменений Pages пока не запускался.
Работа опубликованного фронтенда и настройки облачного Auth не проверены автоматическими сценариями.
Не проводились нагрузочные испытания, независимый security audit и проверки всех браузеров.
Ограничение каталога участников и остальные продуктовые допущения — в `decisions.md`.

При сборке Vite может сообщать о некорректных PURE-комментариях внутри Zod;
сборка завершается успешно, пользовательский код таких предупреждений не создаёт.

Регрессия открытых форм проверяет конфликт задачи и объекта, блокировку повторного сохранения,
явную загрузку актуальной записи и сохранение чужого описания/адреса. Исчезновение последней
страницы проверяется после инвалидации; адаптер воспроизводит PGRST103. Поиск исполнителя
проверен с 1005 дополнительными профилями, имена участников загружаются по ID.
Потеря ответа после создания не создаёт дубль при повторе в той же форме.

Настоящие транзакции подтверждают: разные задачи одного объекта не ждут друг друга;
удаление объекта ждёт активную команду и скрывает результат после её коммита;
перенос в удаляемый объект отклоняется после освобождения блокировки;
конкурентные повторы создания объекта и задачи возвращают тот же ID, у задачи одно начальное событие.
Созданные этим набором тестовые объекты скрываются, их аудит сохраняется.

Диагностический RPC проверен на настоящем API: authenticated отправляет событие,
anon получает отказ, private-схема не экспонируется. PGlite проверяет ограничения полей,
лимит 20 событий в минуту и запрет чтения служебных таблиц. Frontend-тест проверяет,
что исходные сообщения и произвольные URL не попадают в диагностический payload.

Локальное сравнение планов до/после RLS:

| Запрос                      | До, мс | После, мс |
| --------------------------- | -----: | --------: |
| Подсчёт задач, manager      |  68,15 |      2,19 |
| Подсчёт задач, executor     |  67,81 |      2,41 |
| Страница объектов, executor |  68,42 |      0,55 |
| Подсчёт объектов, executor  |  68,41 |      0,45 |

Это единичные локальные измерения без сетевой задержки и конкурентной нагрузки, не SLA.
Полные планы генерируются в .local/query-profile.json. Методика — operations.md.

CI дополнен аудитом зависимостей, настоящими параллельными транзакциями, проверкой
актуальности типов и настоящим UI. Для запуска использует setup:local, который захватывает
вывод CLI с ключами и не печатает доступы. Удалённый GitHub Actions ещё не выполнялся.
Внешние алерты, расписание очистки диагностики, облачное развёртывание и проверка
восстановления резервных копий не настроены; для них нужна инфраструктура эксплуатации.

## Единое поле исполнителя (PEOPLE-02)

Поиск и выбор объединены в один combobox «Исполнитель». В задачу по-прежнему передаётся
только выбранный assignee_id. При отмене поиска сохраняется прежнее назначение.
Проверены выбор стрелками/Enter, Escape без закрытия диалога, отсутствие совпадений,
сохранение и повторное открытие назначения, серверная пагинация без отправки формы.
Поиск за пределами 1000 профилей и форма проверены при ширине 390 px; desktop/mobile
скриншоты просмотрены. Выполнен настоящий цикл Supabase с новым полем.

Проверки: check, build, format:check; 128 Vitest + 3 архитектурных теста;
6 E2E и 1 настоящий UI-сценарий. Схема БД не менялась.
