# План реализации

Статус: локальная реализация завершена; выполненные проверки и внешние зависимости — [verification.md](./verification.md). Источник требований: [spec.md](./spec.md).

## 1. Архитектурные решения

| Область             | Решение                                             | Причина                                                        |
| ------------------- | --------------------------------------------------- | -------------------------------------------------------------- |
| Сборка              | React + TypeScript strict + Vite                    | SPA без ненужного для CRM SSR                                  |
| Навигация           | React Router                                        | Защищённый layout и пять простых маршрутов                     |
| Серверное состояние | TanStack Query                                      | Запросы, мутации, инвалидация и изоляция кэша по пользователю  |
| Данные/Auth         | Supabase JS + генерируемые типы БД                  | Типизированный доступ без отдельной ORM                        |
| Формы               | React Hook Form + Zod                               | Формы и ранняя валидация; SQL остаётся окончательной проверкой |
| UI                  | shadcn/ui + Tailwind CSS                            | Доступные базовые элементы и единообразные формы               |
| Backend             | Supabase Auth + PostgreSQL + Data API/RPC           | Авторизация и транзакции рядом с данными                       |
| Качество            | ESLint, Prettier, TypeScript; проверки FSD-импортов | Проверяемые границы и единый стиль                             |
| Проверки            | pgTAP, Vitest, React Testing Library, Playwright    | Сначала безопасность БД, затем критические сценарии UI         |
| Доставка            | GitHub Actions, GitHub Pages/Vercel, Supabase Cloud | Воспроизводимые проверки и демонстрация                        |

Версии выбираются совместимые на момент начала реализации и фиксируются lockfile.
Redux/Zustand, NestJS, Prisma, очереди и Edge Functions для этого объёма не требуются.
Backend имеет явные границы: API-команды → проверки домена → таблицы/ограничения → аудит.
Это модульная система внутри PostgreSQL, а не набор бизнес-правил в React.

## 2. FSD на фронтенде

```text
frontend/src/
  app/                 # providers, router, query-client, styles
  pages/
    sign-in/ sites/ site-details/ task-details/ my-tasks/
  widgets/             # только при появлении самостоятельных составных блоков
  features/
    auth/              # sign-in/sign-out
    manage-site/       # формы создания, редактирования, удаления
    manage-task/       # форма задачи и назначение
    transition-task/   # переход и комментарий при возврате
  entities/
    session/           # текущий пользователь и профиль
    construction-site/ # DTO, query keys, queries, UI представления объекта
    task/              # DTO, queries, статус, timeline, чистая модель доступных действий
  shared/
    api/               # Supabase client, Database types, общий перевод ошибок
    ui/                # Button, Input, Dialog, FormField, Skeleton, EmptyState
    lib/               # технические утилиты без бизнес-правил
    config/            # типизированные публичные переменные окружения
backend/
  migrations/
  tests/               # database (SQL integration), api (HTTP), sql (pgTAP)
  scripts/
  seed.sql             # только безопасные демонстрационные данные, без паролей
docs/
  spec.md
  implementation-plan.md
  decisions.md         # создать при реализации, записать отличия от плана
  handover.md          # объяснение руководителю и заготовка сдачи
```

- Импорты направлены вниз: app → pages → widgets → features → entities → shared.
- Слайсы одного слоя не импортируют внутренности друг друга. Публичные API — `index.ts`.
- Связанные task/site DTO используют ID; композиция двух сущностей происходит выше,
  без циклических импортов. Общий технический `Database` type допустим в shared/api.
- CRUD-формы остаются предметными; не строим универсальный form/table framework.
- Страницы собирают сценарий; компоненты представления получают props и callbacks.
- Запросы принадлежат сущностям, команды — features; Supabase не вызывается из JSX-компонентов.
- Доменные правила доступных действий — чистые функции; они помогают UI,
  но не заменяют проверки PostgreSQL.
- TanStack Query хранит серверные данные; формы/локальный UI — своё локальное состояние.
  Пользовательский ID входит в query keys; инвалидация затрагивает задачу, историю,
  оба затронутых объекта и мои задачи; при смене сессии кэш очищается.

## 3. Контракты backend

Чтение: SELECT через Data API с RLS и ограниченной пагинацией.
Вложенные задачи/история также должны фильтроваться RLS; политика объектов не даёт доступа ко всем их задачам.

| Команда RPC       | Вход                                                           | Проверки                                                        |
| ----------------- | -------------------------------------------------------------- | --------------------------------------------------------------- |
| `create_site`     | name, address                                                  | Постановщик, длины/trim                                         |
| `update_site`     | id, expected_version, name, address                            | Постановщик, существование, активность, версия                  |
| `delete_site`     | id, expected_version                                           | Постановщик; soft delete объекта и его задач атомарно           |
| `create_task`     | site_id, title, description, assignee_id                       | Постановщик, активный объект, профиль исполнителя; статус `new` |
| `update_task`     | id, expected_version, site_id, title, description, assignee_id | Постановщик; явный whitelist полей без статуса/автора/дат       |
| `delete_task`     | id, expected_version                                           | Постановщик, soft delete                                        |
| `transition_task` | id, expected_version, target_status, comment?                  | Доступ, роль/назначение, переход, обязательный комментарий      |

Все команды возвращают ID и актуальную версию либо изменённую типизированную запись.
Ошибки имеют стабильные коды для UI: валидация, запрещено, запись недоступна, конфликт версии.
Для чужого и несуществующего UUID — одинаковый ответ о недоступности.
История, смена ролей и создание пользователей не получают публичных команд записи.

Для API-функций задать grants явно; для внутренних функций — отдельная неэкспонируемая схема `private`.
Перед миграцией проверять не только RLS, но и права схем, таблиц и функций.
Триггеры с привилегированным доступом к истории не предоставляют пользователю право записи истории.

## 4. Порядок реализации: вертикальные этапы

### Этап 0. Зафиксировать контекст

- Принять или скорректировать допущения из spec.md.
- Создать короткий AGENTS.md: читать спецификацию перед изменениями, соблюдать FSD,
  не ослаблять безопасность ради UI, обновлять требования и проверки вместе с поведением.
- Создать Vite-приложение, env.example, gitignore, алиасы и базовые команды качества.
- Поднять локальный Supabase; настроить отключение регистрации локально и в облаке.

Готовность: пустая страница запускается; сборка/typecheck работают; секретов в исходниках нет.

### Этап 1. Безопасная база и модель статусов

- Миграции в порядке: enums/таблицы/индексы → helpers/RLS/grants → команды/триггеры.
- Явные NOT NULL/FK/CHECK; дефолты времени и версий; защита автора и даты.
- Атомарные переходы и событие создания; проверка конкурентного доступа.
- Подготовить fixture пользователей для локальных тестов и способ ручного создания облачных учёток.
- Сначала выполнить положительные и отрицательные тесты из раздела 5.

Готовность: правила работают без приложения и при прямом обращении с JWT разных пользователей.

### Этап 2. Сквозной пользовательский сценарий

- Провайдер сессии, вход/выход, защищённые маршруты, меню по роли.
- Список объектов → карточка объекта → карточка задачи с историей.
- Страница моих задач для исполнителя.
- Кнопки переходов, форма обязательного комментария, корректная обработка конфликтов.
- Loading/error/empty; недоступная запись; обновление кэша и очистка при выходе.

Готовность: постановщик и два исполнителя проходят полный цикл без утечки данных между аккаунтами.

### Этап 3. Управление и доведение

- Создание/редактирование/удаление объектов и задач; выбор исполнителя.
- Подтверждение удаления с объяснением последствий для задач объекта.
- Пределы текста и обязательность полей в формах согласованы с SQL.
- Базовые клавиатурные взаимодействия, labels, focus диалогов, читаемый layout на узком экране.

Готовность: все экраны и команды ТЗ доступны нужной роли; интерфейс аккуратен и понятен.

### Этап 4. Проверки, демонстрация и сдача

- Прогнать миграции с чистой БД, db tests, lint, typecheck, build и критические UI/E2E проверки.
- Проверить прямые REST/RPC запросы в обход UI на облачном проекте.
- Развернуть SPA с fallback маршрутов; настроить Supabase URL/redirect URL и публичные env.
- Подготовить минимум 1 постановщика, 2 исполнителей, 3 объекта и задачи во всех статусах.
  Статусы для демо получать реальными разрешёнными командами, с согласованной историей.
- README: требования, запуск, env, миграции, типогенерация, команды проверок, архитектура.
- decisions.md: допущения и фактические ограничения; handover.md: полстраницы простым языком.
- Подготовить одно сообщение для hh.ru: URL, доступы, GitHub, объяснение, решения/остаток.

Готовность: ревьюер воспроизводит запуск и проверяет оба уровня — интерфейс и базу.
Фактическая публикация требует доступных аккаунтов Supabase, GitHub и хостинга;
отсутствие доступа фиксируется как внешняя зависимость, не как выполненная доставка.

## 5. Матрица обязательных проверок

Основной объём — интеграционные проверки БД под ролями `anon`/`authenticated`
с JWT claims пользователей, а не только запуск SQL владельцем базы.

| Группа         | Сценарии                                                                                                  |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| Видимость      | Аноним ничего не видит; постановщики видят всё; исполнитель A не читает задачи и историю B                |
| Общий объект   | A и B имеют задачи на одной стройке; каждый видит только свои задачи, история не протекает                |
| Профили        | Нельзя повысить свою роль/подменить metadata; исполнителю не доступен общий каталог пользователей         |
| Команды        | Исполнителю запрещены CRUD и переназначение; постановщику разрешены, поля автора/дат недоступны           |
| Переходы       | Все 6 допустимых переходов, запрещённые пары, неверная роль, чужой исполнитель, no-op                     |
| Комментарий    | Возврат с NULL/пустым/пробельным комментарием отклонён; с текстом разрешён                                |
| Аудит          | Нельзя INSERT/UPDATE/DELETE историю; actor/time/from берутся из БД; ошибка не создаёт событие             |
| Прямой API     | PATCH статуса и прочих полей в таблице запрещён; RPC не принимает подставного actor                       |
| Конкуренция    | Два запроса одной версии: один успех, один конфликт; одно событие; нет потерянного редактирования         |
| Переназначение | Старый исполнитель теряет чтение/переходы, новый получает доступ; статус не сбрасывается                  |
| Удаление       | Soft-deleted сущности нельзя читать/менять; объект удаляется вместе с видимостью задач; аудит сохраняется |
| Сессия/UI      | Вход/выход/смена пользователя; правильные кнопки; возврат с комментарием; данные не остаются в кэше       |

Vitest: чистая модель доступных действий и обработка ошибок/конфликтов.
RTL: обязательность комментария и ключевые состояния карточки.
Playwright: один сквозной цикл с постановщиком и исполнителями, включая изоляцию.
Конкуренцию дополнительно проверить двумя одновременными API-запросами, а не имитацией в одной транзакции.
В CI: чистое применение миграций, тесты БД, lint/typecheck/build, критический E2E.

## 6. Бюджет времени и приоритет

Целевой timebox задания — 180 минут после готовности окружения и доступов:

| Работа                                           | Минуты |
| ------------------------------------------------ | -----: |
| Проверка спецификации и каркас                   |     15 |
| База, RPC, RLS, проверки безопасности            |     60 |
| Пять экранов, CRUD и workflow                    |     65 |
| Сквозная проверка, deploy, демоданные, документы |     40 |

Это напряжённая оценка для тестового, а не обещание production-ready системы за 3 часа.
Архитектура пригодна для расширения; эксплуатационная зрелость требует отдельного времени.
При задержках сокращаем оформление и необязательные удобства. Обязательные функции и безопасность
не объявляем готовыми без реализации и проверки; превышение оценки или незавершённость указываем честно.
Расширение тестовой матрицы и полная автоматизация CI могут потребовать дополнительного времени,
которое согласуется отдельно. Критические негативные проверки безопасности остаются обязательными.

## 7. Правила SDD при дальнейшей работе

1. Выбрать требование по ID и описать ожидаемый результат.
2. Зафиксировать контракт входов/выходов, доступ и отказные сценарии.
3. Добавить соответствующую проверку; для БД обязательно проверить обход интерфейса.
4. Реализовать минимальный законченный вертикальный сценарий.
5. Прогнать относящиеся к изменению проверки; при изменении схемы обновить типы.
6. Обновить документацию и таблицу выполнения: planned / implemented / verified с доказательством.
   Актуальный статус каждого требования и доказательства — в `verification.md`.
