# Правила реализации

Перед изменением поведения читать `docs/spec.md` и `docs/implementation-plan.md`.
Соблюдать SDD: требование → контракт → проверка → код; изменения требований фиксировать в спецификации.
Соблюдать FSD и публичные API слайсов. Shared не содержит правил CRM.
Клиентский код находится в `frontend/`, серверная схема/команды/тесты — в `backend/`.
CLI Supabase запускать через `backend/scripts/cli.mjs`; `.local/` — генерируемый runtime, не исходники.
Доступ и workflow проверяются PostgreSQL; скрытые кнопки не являются защитой.
Не добавлять секреты, пароли, service_role или обходы RLS в клиент/репозиторий.
Изменения схемы сопровождаются тестами прав и обновлением типов.
Перед сдачей: `npm run check`, `npm test`, `npm run build`; интеграционные E2E отдельно.
При доступном Docker после изменений БД выполнять `npm run db:test` и `npm run test:api:local`;
после изменений workflow/UI — `npm run test:ui:local`. Форматирование: `npm run format:check`.
Локальные доступы и env не выводить в логи. Существующие пользовательские данные не сбрасывать;
для изменения схемы добавлять миграции.
Не выдавать непроверенные сценарии за выполненные. Дефекты устранять до завершения работы.
